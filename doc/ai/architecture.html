mp-darkmode 项目完整逻辑解析

微信公众平台 Dark Mode 转换算法。本文档梳理项目的整体架构、核心算法与模块协作关系，供开发与维护参考。

一、项目定位

mp-darkmode 是微信公众平台（WeChat）开源的一套 Dark Mode（深色模式）颜色转换算法库。核心目标：在不修改原始 HTML / 内联样式的前提下，通过 JS 遍历 DOM 节点、动态生成一套 <style> 样式表并注入 <head>，把一篇原本为 Light Mode（浅色）设计的公众号文章「自动翻译」成一套视觉舒适的深色配色。

  • 产物：UMD 格式的 dist/darkmode.min.js，全局暴露 Darkmode 对象（也支持 AMD/CMD require）。
  • 构建：webpack + babel + TypeScript，npm run build 打包并把 .d.ts 复制到 dist。
  • 依赖：color / colorjs.io（颜色解析）、color-blend（混合模式）、color-name（颜色名）、object.hasown（低版本 iOS polyfill）。

二、对外 API · src/darkmode.ts

DarkMode 接口对外暴露 8 个方法：

方法作用
run(nodes, opt)初始化配置 + 立即执行转换（最常用，= init + set + switchToDarkmode）
init(opt)只初始化配置（只能调用一次），并注册系统深色模式媒体查询监听
convertBg(nodes)二次处理「背景图 / 渐变」下的文字节点（延迟背景判断场景）
updateStyle(node, styles)运行时更新单个节点的样式并重新转换
getContrast(c1, c2)计算两个颜色对比度 [1, 21]
extend(pluginList)挂载插件
reset(nodes)卸载所有状态、移除注入的样式表、清理节点上的私有属性
validate(container, opt, filter)校验深色模式效果（低对比度 / 文字背景渐变 / 白名单）

核心调度函数 switchToDarkmode

整个流程的中枢，通过 opt.type 分两种模式：

type: 'dom' 处理节点

  • 先根据 config.mode 或系统媒体查询 mql.matches 决定 sdk.isDarkmode。
  • 遍历所有节点：先清理节点上原有的 js_darkmode__ class（防止复制文章时把旧暗黑 class 带过来），再调用 sdk.convert(node) 得到该节点的 CSS，累加到样式表。
  • 首屏优化逻辑（needJudgeFirstPage）：用 getBoundingClientRect() 判断节点在首屏前 / 首屏内 / 首屏后。首屏内的节点先隐藏（visibility），单独写「首屏样式表」并优先显示，避免用户看到「浅色闪一下再变深色」的闪烁；一旦遍历到首屏之后的节点，就写入首屏样式、显示首屏节点、执行 showFirstPage 回调，之后不再判断首屏。

type: 'bg' 处理背景

  • 配合 convertBg，处理背景图/渐变区域内的文字节点，重新计算这些子节点的继承颜色属性并再次转换。

Light Mode 时：如果没有强制指定 mode，会把节点转移到「延迟处理队列」，等系统切到深色时再处理。

三、核心转换算法 · src/modules/sdk.ts + color.ts

项目的灵魂。设计原则见 doc/cn/principle.md：只处理 4 类颜色——背景色、字体色、边框色、字体阴影色。

关键概念：感知亮度（Perceived Brightness）

brightness = (R×299 + G×587 + B×114) / 1000   // W3C AERT 公式

算法不是简单反色，而是基于人眼感知亮度来调整，并全程考虑透明度（用 mixColors 把半透明色叠加到背景上算出真实观感色）。

convert(el) 的处理流程

  1. 白名单过滤（MPCPS / IFRAME 标签，或带白名单属性的节点直接跳过）。
  2. 从内联 style.cssText 解析出 [key, value] 列表，过滤出支持的颜色属性（CSS_PROP_LIST），并排序（color 放最后、-webkit-text 放最前、background-image 在 background-color 后）。
  3. 特殊兜底：table/tr/td/th 的 bgcolor 或特定 class、<font color>、-webkit-text-fill-color/-webkit-text-stroke 都被归一化成内联颜色来处理。
  4. 逐个颜色值用正则 COLOR_REGEXP 匹配，调用 _adjustBrightness 转换，!important 会被清除后统一由生成的 CSS 加回。

三个调整函数（由 _adjustBrightness 分发）

1. _adjustBackgroundBrightness（背景 / 字体阴影）

  • 黑白灰(饱和度=0)且亮度 > 40，或感知亮度 > 250（白色）→ 做亮度取反（白底翻成默认深色底 #191919）。
  • 感知亮度 > 190 → 压到 190。
  • HSL 亮度 < 22 → 抬到 22（纯黑背景适当提亮，避免死黑）。

2. _adjustTextBrightness（字体 / 边框）

  • 接近白色（亮度 ≥ 250）→ 不动，保持高亮。
  • 与背景的感知亮度差 ≥ 65（MIN_LIMIT_OFFSET_BRIGHTNESS）→ 不动（对比足够）。
  • 差值不足 → 亮背景调暗字、暗背景调亮字，优先通过翻转 HSL 亮度达成，再用 adjustBrightnessTo 精确调到目标感知亮度，保证可读性。

颜色继承机制（关键设计）

节点上挂了一批以随机数结尾的私有 DOM 属性（constant.ts 定义），用于父子节点间透传颜色：

属性含义
COLORATTR / BGCOLORATTR算法算出的新色（已 mix）
ORIGINAL_COLORATTR / ORIGINAL_BGCOLORATTR原始 Light Mode 色值
BGIMAGEATTR是否有背景图标记
BGGRADIENT_MIXCOLORATTR渐变 mix 后的色
COMPLEMENTARY_BGIMAGECOLORATTR背景图补色

处理某节点背景色后，会把「新背景色 / 原背景色 / 计算出的合适字体色」写到它自己和所有子节点上（getChildrenAndIt），这样子节点在计算自身文字对比度时能拿到真实的背景上下文。只有背景色没字体色的节点会追加一条计算出的字体色。

四、背景图与渐变的特殊处理

  • 背景图（处理 2）：深色下不能直接反色图片。策略是在图片下方补一层 Light Mode 原背景色（linear-gradient(imgBgColor, imgBgColor) 多层背景），保证图片上文字仍可读；SVG 跳过。
  • 渐变色：先用 mixColors(colors, 'mix') 算出一个代表色，深色模式下统一转成纯色处理。
  • 位置判断（bgNodeStack.ts + textNodeQueue.ts）：背景图节点入「背景堆栈」，文字节点入「文字队列」。因为背景图影响的是它视觉覆盖区域内的文字（不一定是 DOM 子节点），所以要用 getBoundingClientRect() 做矩形相交判断（contains），确定哪些文字落在背景图区域内。delayBgJudge 支持把这个判断延后到 convertBg 阶段（解决 DOM 前后不一致，用 update 重新绑定节点）。

五、样式生成与注入 · cssUtils.ts

  • 不改内联样式，而是给节点加 class（js_darkmode__序号），生成 .js_darkmode__N{ color: xxx !important; } 形式的规则。
  • 选择器前缀：强制 mode:'dark' 时前缀 html.data_color_scheme_dark；否则整段包在 @media (prefers-color-scheme: dark) {} 里，跟随系统。
  • 分「首屏样式表」和「非首屏样式表」两份，配合首屏优化。
  • 最终 document.head.insertAdjacentHTML 注入 <style id="js_darkmode_style__时间戳_序号">。noEmit 可关闭注入（用于服务端/自定义场景）。isFinish 标记是否已运行过。

六、插件系统 · plugins.ts

  • 从 v1.1.0 起支持，Darkmode.extend([pluginFactory])。
  • 插件继承 PluginBaseAbstract，可用 loopTimes / isDarkmode / addCss。
  • 提供 9 个钩子（PLUGIN_HOOK），分别在「转换节点前 / 转换文字色后 / 转换节点后」触发，并区分普通转换、updateStyle 更新、reset 重置三种场景。典型用途：过滤 DOM 属性、注入自定义样式。

七、校验器 · validator.ts

validate 用 TreeWalker 遍历容器，跳过隐藏/背景图/SVG 节点，检测三类问题并返回结果列表：

  1. low-contrast：文字与背景对比度低于阈值（默认 1.5）。
  2. no-gradient：文字背景使用了渐变。
  3. whitelist：命中白名单会被跳过转换的提醒。

节点可用 data-ignore-dm 属性声明忽略某规则。

九、一句话总结整体逻辑

遍历传入的 DOM 节点 → 解析每个节点内联样式里的颜色 → 基于「感知亮度 + 透明度混合 + 父子颜色继承」算法，把背景/文字/边框/阴影色重算成深色配色（背景图则补底色保可读性）→ 通过给节点加 class、生成 @media (prefers-color-scheme: dark) 或 html.data_color_scheme_dark 作用域的 <style> 并注入 head 来生效 → 全程配合首屏优化避免闪烁、插件扩展和效果校验，且不侵入原始 HTML。

十一、_adjustTextBrightness 逐行拆解

这是字体/边框颜色的核心，目标：在深色背景上算出既不刺眼、又对比足够、且尽量保留原色相的字体色。它通过「HSL 明度翻转 → 递归再判断 → 感知亮度精调」的两段式策略实现。

关键前提

  • _maxLimitOffsetBrightness = max(默认深色字感知亮度 − 默认深色底感知亮度, 0)，即「基准对比亮度差」，用作字体与背景亮度差的上限（避免过曝刺眼）。
  • 阈值：WHITE_LIKE=250、MIN_LIMIT_OFFSET=65、HIGH_BGCOLOR=100、HIGH_BLACKWHITE_HSL=40。
  • opt 参数是「是否处于递归调用」的开关，决定两处行为（见下表 L2 / L9 / L11）。
_adjustTextBrightness(textColor, bgColor, opt?) {
  const textColorAlpha = opt?.alpha || textColor.alpha();                         // L1
  const textColorMix = opt ? textColor : mixColors([bgColor, textColor]);         // L2
  if (textColorMix === null) return null;                                         // L3
  const textColorMixRgb = textColorMix.rgb().array();                             // L4
  const textColorMixHsl = textColorMix.hsl().array();                             // L5
  const textPerceivedBrightness = getColorPerceivedBrightness(textColorMixRgb);   // L6
  const bgColorPerceivedBrightness = opt?.bgColorPerceivedBrightness              // L7
      || getColorPerceivedBrightness(bgColor.rgb().array());
  const offset = Math.abs(bgColorPerceivedBrightness - textPerceivedBrightness);  // L8

  if (textPerceivedBrightness >= WHITE_LIKE_COLOR_BRIGHTNESS)                      // L9  分支A
    return opt ? getFrontColor(textColor, bgColor, textColorAlpha) : textColor;

  if (offset > _maxLimitOffsetBrightness                                          // L10 分支B
      && bgColorPerceivedBrightness <= _defaultDarkBgColorBrightness + 2)
    return getFrontColor(
      adjustBrightnessTo(_maxLimitOffsetBrightness + bgColorPerceivedBrightness, textColorMixRgb),
      bgColor, textColorAlpha);

  if (offset >= MIN_LIMIT_OFFSET_BRIGHTNESS)                                       // L11 分支C
    return opt ? getFrontColor(textColor, bgColor, textColorAlpha) : textColor;

  if (bgColorPerceivedBrightness >= HIGH_BGCOLOR_BRIGHTNESS) {                     // L12 分支D 亮底
    if (textColorMixHsl[2] > 90 - HIGH_BLACKWHITE_HSL_BRIGHTNESS) {                // L13 (L>50)
      textColorMixHsl[2] = 90 - textColorMixHsl[2];                               // L14 明度翻转↓
      return _adjustTextBrightness(Color.hsl(...textColorMixHsl), bgColor, {...});// L15 递归
    }
    return getFrontColor(                                                         // L16
      adjustBrightnessTo(min(_maxLimitOffsetBrightness, bgBrightness - 65), textColorMixRgb),
      bgColor, textColorAlpha);
  } else {                                                                        // L17 分支E 暗底
    if (textColorMixHsl[2] <= HIGH_BLACKWHITE_HSL_BRIGHTNESS) {                    // L18 (L<=40)
      textColorMixHsl[2] = 90 - textColorMixHsl[2];                               // L19 明度翻转↑
      return _adjustTextBrightness(Color.hsl(...textColorMixHsl), bgColor, {...});// L20 递归
    }
    return getFrontColor(                                                         // L21
      adjustBrightnessTo(min(_maxLimitOffsetBrightness, bgBrightness + 65), textColorMixRgb),
      bgColor, textColorAlpha);
  }
}

逐行含义

行说明
L1取文字透明度。递归时用传入的 alpha（原始文字透明度），保证反推前景色时透明度一致。
L2opt 开关关键点①：首次调用（无 opt）需把文字色与背景 mixColors，得到「文字叠加在背景上的真实观感色」（处理半透明）；递归时 textColor 已是纯色 HSL，直接用。
L4–L6把观感色转 RGB / HSL，算文字感知亮度（W3C 公式）。
L7背景感知亮度：递归时复用首次算好的值（避免重算，也保证判断基准一致）。
L8文字与背景的感知亮度差绝对值 offset——衡量对比是否足够。
L9 分支A保持高亮：文字观感亮度 ≥ 250（接近白色），深色下白字本就好看，不动。opt 开关关键点②：首次直接返回原 textColor（一点不改）；递归态返回 getFrontColor（把翻转后的观感色反推回带透明度的前景色）。
L10 分支B抑制过高对比：当背景很暗（≈默认深底，≤ 深底亮度+2）且对比差已超过基准上限，说明是「纯白字 + 纯黑底」这类过曝组合，把文字感知亮度压到 背景亮度 + 基准差，对齐默认深字/深底的舒适对比。
L11 分支C对比已足够：offset ≥ 65 就不再调整（opt 开关关键点③，同 L9 的返回规则）。
L12 分支D亮背景 → 调暗字（背景亮度 ≥ 100）。
L13–L15若文字 HSL 明度 > 50：先翻转明度 L = 90 − L（把亮字拉暗，保留色相/饱和度），再递归重新判断。翻转后 L < 40，递归时若对比够了走 C 返回；否则落到 L16 精调。
L16用 adjustBrightnessTo 把文字感知亮度精确设为 min(基准上限, 背景亮度 − 65)，即比背景暗 65 且不超过基准，再 getFrontColor 反推带透明度前景色。
L17 分支E暗背景 → 调亮字（背景亮度 < 100，深色模式主场景）。
L18–L20若文字 HSL 明度 ≤ 40：翻转 L = 90 − L（把暗字拉亮）后递归。翻转后 L ≥ 50，不会再满足翻转条件。
L21精调到 min(基准上限, 背景亮度 + 65)，即比背景亮 65。

递归为什么安全（最多 2 层）

翻转只在「亮底 & L>50」或「暗底 & L≤40」时发生，翻转后明度必然越过该阈值（50↔40 两侧），递归再进来时不再满足翻转条件，只会走分支 C 返回或走精调（L16/L21）返回。因此递归深度最多为 2，不会死循环。

设计意图：先用「HSL 明度翻转」做粗调——它保留色相与饱和度，让转换后的字仍带原来的「颜色个性」（如红字翻转后仍是红系）；只有翻转后对比仍不足时，才用感知亮度精调兜底。两段式兼顾了可读性与色彩保真。

十二、背景图位置判断完整时序（矩形相交 + 延迟队列）

背景图/渐变影响的是它视觉覆盖区域内的文字，而这些文字未必是它的 DOM 子节点（可能是绝对定位、兄弟层叠等）。因此不能靠 DOM 树关系，只能用屏幕矩形相交来判定「哪些文字落在背景区域内」。

矩形相交算法（bgStack.contains）

取文字节点 rect 与背景节点 bgRect（均来自 getBoundingClientRect()），用「不相交条件取反」判断相交：

相交 = !(
    rect.top    >= bgRect.bottom   // 文字在背景下方
 || rect.bottom <= bgRect.top      // 文字在背景上方
 || rect.left   >= bgRect.right    // 文字在背景右侧
 || rect.right  <= bgRect.left     // 文字在背景左侧
);  // 四个「分离」条件都不成立 ⇒ 两矩形重叠 ⇒ 文字落在背景区域内

命中的背景项从 _stack 中 splice 移除（一个背景处理过对应文字后即出栈），并执行其回调（给区域内节点标记 COMPLEMENTARY_BGIMAGECOLORATTR 补色、输出背景补色 CSS）。rect 会缓存到 item.rect 避免重复回流。

两种时序：立即判断 vs 延迟判断

立即判断（delayBgJudge = false，默认）延迟判断（delayBgJudge = true）
入栈/入队时 背景图 push 时 updated = true，立即可参与相交判断 背景图 push、文字 tnQueue.push 时 updated = false，暂不判断
文字节点处理 convert 末尾直接 bgStack.contains(el, cb)，当场定位 convert 末尾 tnQueue.push(el) 入队，推迟
触发定位 随节点遍历同步完成 调用方随后调 convertBg(nodes) 统一处理

延迟判断为什么需要 update()

延迟场景下，「首次处理时的节点对象」与「最终渲染进 DOM 的节点对象」可能不是同一个引用（例如内容经过二次渲染 / 富文本被重建）。因此 convertBg 第一步先做重绑定：

convertBg(nodes)
   │
   ├─ bgStack.update(nodes)
   │     └─ 遍历栈中 updated=false 的项，用其 className（js_darkmode__bg__N）
   │        在新传入的 nodes 里 querySelector 匹配，找到就 item.el = 新节点, updated = true
   │
   ├─ tnQueue.update(nodes)   （同理：用 js_darkmode__text__N 重绑文字节点）
   │
   └─ switchToDarkmode(type:'bg')
         └─ tnQueue.forEach(text):        // 只遍历已 updated 的
              bgStack.contains(text, cb)  // 用最终布局的 rect 做相交判断
                 ├─ 命中 → 输出背景 CSS + 执行回调
                 └─ 重置该背景下所有「新老」子节点的继承属性(COLORATTR/BGCOLORATTR/…)后重新 convert

要点：只有 updated = true 的项才参与遍历/判断；未能在新 nodes 中重绑的项会被跳过，避免对失效节点误操作。

十三、首屏优化执行顺序与闪烁规避原理

问题背景：若逐个节点转换并立即注入样式，用户会看到内容先以浅色渲染、再一块块变深的闪烁（FOUC）。首屏优化的目标是让用户第一眼看到的首屏内容就是最终深色态。

核心手段：先隐藏 → 算好 → 一次性显示

使用方应让首屏节点初始为 visibility: hidden。算法在遍历时对每个节点用 getBoundingClientRect() 判断它相对首屏（PAGE_HEIGHT）的位置，分三类分流：

遍历 node，rect = node.getBoundingClientRect()

┌─ top ≤ 0 且 bottom ≤ 0（首屏「上方」，已滚过/不可见）
│     └─ addCss(convert(node))               → 计入「非首屏样式」（内存累积）
│
├─ top∈(0,PAGE_HEIGHT) 或 bottom∈(0,PAGE_HEIGHT)（首屏「内」）
│     ├─ domUtils.addFirstPageNode(node)     → 记录首屏节点
│     └─ addCss(convert(node), true)         → 计入「首屏样式」（内存累积）
│
└─ 其它（首屏「下方」，理论上整轮最多进入一次）★关键转折点★
      ├─ config.needJudgeFirstPage = false   → 此后不再判断首屏
      ├─ cssUtils.writeStyle(true)           → ① 立即注入「首屏样式表」
      ├─ domUtils.showFirstPageNodes()       → ② 把首屏节点 visibility 置 visible（一次性显示）
      ├─ config.showFirstPage?.()            → ③ 执行首屏完成回调
      └─ addCss(convert(node))               → 当前（首屏下方）节点计入非首屏样式

图：遍历过程中首屏前 / 内 / 下方三类节点的分流与「转折点」触发时机

遍历结束后的收尾

遍历结束：
   ├─ if (needJudgeFirstPage || (!needJudgeFirstPage && !domUtils.showFirstPage))
   │        config.showFirstPage?.()     // 兜底回调：
   │        // 情况1 needJudgeFirstPage 仍为 true → 正文没超过一屏，从未遇到「转折点」
   │        // 情况2 不判首屏且没做首屏优化
   ├─ cssUtils.writeStyle()              // 注入「非首屏样式表」（含首屏样式一并补上）
   └─ domUtils.emptyFirstPageNodes()     // 清空首屏节点记录

闪烁规避的三个关键点

  1. 首屏内容「先隐藏、批量算好、一次性显示」：越过首屏边界的瞬间才 writeStyle(true) + showFirstPageNodes()，用户一次性看到完整深色首屏，不经历浅色闪现与逐块变色。
  2. 样式分两批、延迟真正注入：addCss 只在内存累积字符串，writeStyle 只在「越过首屏边界」和「遍历结束」两个时机真正 insertAdjacentHTML 注入 <style>，减少重排与首屏渲染阻塞。首屏样式优先注入、非首屏样式延后，保证首屏尽快就绪。
  3. 只判断一次首屏：一旦遇到首屏下方节点即置 needJudgeFirstPage = false，后续节点全部走「非首屏」路径，避免持续调用昂贵的 getBoundingClientRect()（触发回流）。
与延迟背景判断的配合：Light Mode 首次加载会把 needJudgeFirstPage / delayBgJudge 复位，并把节点转入延迟队列（domUtils.delay()）；待系统真正切到深色时再走完整的首屏优化 + 背景定位流程（§12）。
