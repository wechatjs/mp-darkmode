ProseMirror × mp-darkmode 适配方案

用 mp-darkmode 算法为 ProseMirror 架构编辑器做 Dark Mode 适配。本文档为最新定稿，作为算法侧改造与编辑器接入的实现总纲。

背景与目标

现状算法通过「给节点加 className + 注入 <style> + 作用域选择器」生效（见 算法架构文档）。这在只读文章里没问题，但在编辑器里直接把 className 写进真实 DOM 会出问题：

根因：ProseMirror 的视图 DOM 由它根据文档模型（doc）渲染和复用，外部直接改 DOM（加 class / 改 inline）会与 PM 的渲染打架，且被 DOMObserver 误当成用户编辑捕获；而动态 className 又不在 schema 的 parseDOM 白名单里，split / 粘贴 / 重渲染都会让这套样式与文档模型错位。

目标：复用算法成熟的颜色转换与 CSS 产出能力，但让 Dark Mode 的生效方式回到 PM 可管理的范畴，且不污染文档（doc 恒存 Light Mode，保存即 LM）。

一、总体架构

一句话：复用算法的全部 CSS 产出，但 class 不直接写 DOM，而是交给 ProseMirror 的 Decoration 挂到节点上；Dark Mode 开关由 <html> 上的一个 class 控制。

  • 算法以 mode:'dark' 运行，照常生成 html.data_color_scheme_dark .js_darkmode__N{…!important} 规则并注入 <head> 的 <style>（全局视图资源，不进 doc）。渐变 mix、背景图多层补色、-webkit-text 描边等复杂能力全部现成复用。
  • class 不写真实 DOM：通过 setClass 钩子接管，算法算出的 class 串交给调用方，由调用方用 Decoration 挂到节点上（而非写进 DOM / doc）。
  • 块级 class 用 data-dm-class attr 承载（见 §四），使 split 等编辑后能被 PM 原生继承。
  • DM 总开关：给 <html> 加/删 data_color_scheme_dark（即算法常量 HTML_CLASS）。加 class 瞬间全文切深、删即回浅，doc 完全不动。
  • doc 恒存 LM：Decoration 是 PM 视图层每次渲染重新应用的、绝不进 doc；复制粘贴走 doc 序列化天然得到 LM；保存直接存 doc（LM）无需还原。

二、关键业务前提

  • 禁色板：用户不能选中已有文本改 color / bgColor → 日常输入 / split 不产生新颜色、无颜色继承的级联重算。
  • 但粘贴外部片段会带入自定义颜色（如红字片段粘进空编辑器），且会出现渐变背景 / 背景图 / 文字描边等复杂内容 → 粘贴片段必须跑完整算法转换。

三、核心机制

3.1 class 交给 Decoration，而非写 DOM

算法内部 addClass 的自定义路径最终调 config.setClass(node, 整串)。调用方在 setClass 钩子里拿到的是算好的完整 class 串（已含 js_darkmode__N / js_darkmode__bg__N）：

  • 钩子里不写真实 DOM，而是把「节点 → class 串」记录下来（块级写入 data-dm-class attr，见 §四）。
  • 整串覆盖，无需 diff；如需区分 dm class 与业务 class，判 js_darkmode__ 前缀即可（可选）。

3.2 Decoration.node 直接挂原节点，不创建包裹元素

实测确认（§九 Q3）：Decoration.node(from, to, {class}) 把 class 直接加在该节点自己渲染出的 DOM 元素上（要求 from/to 恰好跨越一个 node），不创建任何包裹元素。因此 bgColor / bgImage(多层) / border / boxShadow 全部集中在同一个原节点，不存在包裹嵌套导致的样式重叠。

会产生 <span> 包裹的只有 Decoration.inline（用于 text 的文字色 / 描边），这是 text 本来就该有的 span，与 block 级样式天然分层、互不干扰。

3.3 <html> class 作为 DM 总开关

算法以 mode:'dark' 生成的规则带 html.data_color_scheme_dark 作用域前缀（实测 §九 Q2 命中）。给 <html> 加/删该 class 即可整体切换深浅，且不触碰 doc。

新决定（钩子覆盖 <html>）：算法当前对 <html> 的 class 操作（darkmode.ts L260 add / L348 remove）是直连 document.getElementsByTagName('html')[0].classList、未走 setClass 钩子的。本方案要求改为走 setClass 钩子，并把常量 HTML_CLASS（data_color_scheme_dark）暴露给调用方——调用方在 setClass 里判断是否 <html> 节点来决定行为，并自行决定何时给 <html> 加 HTML_CLASS 作为总开关。详见 §七。

四、data-dm-class 承载块级 class

块级节点的 dm class 存进一个 data-dm-class attr（存的是 class 名串，不是颜色样式；颜色样式仍在全局 <style> 里）。这样 split 等编辑后，ProseMirror 原生会把 attr 复制给新块，新块自动带上正确的 dm class，继承零回溯逻辑。

环节做法
首次全量对视图 DOM 跑算法（mode:'dark' + setClass 钩子）→ 钩子拿到整串 class → 写进对应 node 的 data-dm-class attr
生成 decoration遍历块节点，读 node.attrs['data-dm-class'] → Decoration.node(pos, pos+size, {class: 该串}) 直接挂原节点
回车 splitPM 原生把 data-dm-class 复制给新块 → 新块天然带正确 dm class → decoration 重建直接读到，零回溯
DM 总开关给 <html> 加/删 HTML_CLASS（加即深色、删即回浅色，doc 不动）
保存序列化时过滤掉 data-dm-class（toDOM / clipboard 不输出）→ 存进后台的仍是纯 LM
粘贴外部transformPasted 对片段跑算法 → 写入各节点 data-dm-class
schema 注意：相关 block node 要加 data-dm-class attr 定义，且 toDOM 不渲染它——它只作 doc 模型里的数据载体，由 Decoration.node 读取后挂到视图；不渲染才能不被 DOMObserver 看到、不被保存带出。

五、两类 Decoration 与维护（混合策略）

类型承载生成维护
block（背景 / 边框 / 阴影 / 背景图） data-dm-class attr → Decoration.node 读各块 attr 直接挂原节点 每次 docChanged 按块重建（极廉价，2000 段实测 1.2ms）——天然解决 split / 合并 / 拖拽的块边界变化
text（文字色 / 描边） Decoration.inline（class + !important） 映射到文字区间 走 DecorationSet.map 增量跟随

为何 block 用「重建」而非「map」：实测（§九 Q1）node decoration 在 split 后连原段也会失效（它精确绑定「跨越某个 node」，块 nodeSize 一变 map 后即丢弃）；而按块重建既廉价又天然正确。inline 则 map 有效、文字量大，走增量更划算。

六、运行时数据流

① 首次全量
   对编辑器视图 DOM 跑算法（mode:'dark' + setClass 钩子）
     → 算法注入全局 <style>（html.data_color_scheme_dark .js_darkmode__N{…}）
     → setClass 钩子拿到整串 class → 写入对应 block node 的 data-dm-class attr
     → 遍历块节点读 attr → Decoration.node 挂 class；text 走 Decoration.inline
   DM 总开关：给  加 HTML_CLASS（经 setClass 钩子）

② 日常输入 / split  —— 不跑算法
   block：data-dm-class 被 PM 原生复制给新块 → node decoration 按块重建读到
   text ：inline decoration 走 DecorationSet.map 跟随

③ 粘贴外部复杂片段
   transformPasted → 对片段复用 run(片段节点, opt, container) 跑算法
     ├ run 内部先 rebuildAncestorExpando(container)：从 container 向上遍历到根、
     │   自顶向下读各祖先 LM 背景逐级 mix，把继承 expando 写到【片段顶层节点】
     └ 再 convert 片段 → 写入各节点 data-dm-class → 生成 decoration

④ 保存
   doc 恒 LM；序列化过滤 data-dm-class → 存进后台的是纯 LM

七、算法侧要做什么

本路线复用算法现有的完整 CSS 产出能力，改动很小，核心是「让 class 操作全部可被钩子接管」。

  1. <html> class 操作改走 setClass 钩子（待办）：
    • darkmode.ts L260 document.getElementsByTagName('html')[0].classList.add(HTML_CLASS)、L348 的 classList.remove(HTML_CLASS) 现在直连 DOM、未走钩子，需改为经 setClass（或等价的可接管路径）。
    • 调用方在 setClass 钩子里判断是否 <html> 节点来决定是否真的加 class（编辑器场景由调用方自行控制 <html> 开关时机）。
  2. 暴露 HTML_CLASS 给调用方（待办）：把常量 HTML_CLASS（data_color_scheme_dark）对外导出，调用方据此决定何时给 <html> 加该 class 作为 DM 总开关。
  3. 配置 mode:'dark'：使算法生成带 html.data_color_scheme_dark 作用域的规则并注入 <style>（全局视图资源，不进 doc）。
  4. 粘贴场景：run 增加第三个可选参数 container: HTMLElement（待办）：
    • 粘贴片段复用 run(片段节点, opt, container)。第二次 run 的 init 因 config.hasInit 已 true 被安全跳过（不重复注册监听/重置配置），switchToDarkmode 的 force 会重置 isFinish 再跑一遍。
    • 新增 rebuildAncestorExpando(container)：从 container 沿 parentNode 向上遍历到根（方案 A），自顶向下读各祖先 inline 背景色（doc 恒 LM，读到即 LM）、用 mixColors 逐级叠加，算出「到 container 处的 DM / 原始背景上下文」。
    • 关键：继承 expando 要写到【片段顶层节点】（不是 container）——因为 convert(片段节点) 读的是片段节点自己的 expando，且 expando 不会自动父传子（靠 convert 处理父时主动写给子）。写到片段顶层后，convert 才能正确继承祖先背景并往片段内子孙传递。
    • 调用时机：container 相关处理须放在 domUtils.set(nodes) 之后、switchToDarkmode 之前（不能放 init，因第二次 run 的 init 被跳过）。
  5. 其余 DOM 写操作走钩子、不碰真实 DOM：setClass 接管块/文字 class（交给调用方记录，不写 DOM）；setStyle（清 !important 等）传 no-op 兜底；setAttr / getAttr 用默认 expando property（MutationObserver 监听不到，rerender 丢失无妨）。
  6. 编辑器场景配置：needJudgeFirstPage:false、delayBgJudge:false（首屏优化/背景延迟判断对编辑器无意义）。
不需要之前设想的 setDmStyle 钩子 / diff 直出 / 专门的 convertFragment API——直接复用算法现有 CSS 产出即可。但「对粘贴片段跑算法转换」这个能力仍然需要，只是改为复用 run(nodes, opt, container) 实现（见上条），而非新造 API。

八、调用方（编辑器）要做什么

  1. schema：相关 block node 增加 data-dm-class attr 定义，toDOM 不渲染它。
  2. DM 插件（核心）：维护 DecorationSet
    • init：对视图 DOM 跑算法（mode:'dark' + 钩子）→ setClass 回调里把整串 class 写进对应 block 的 data-dm-class attr → 遍历块读 attr 生成 Decoration.node；text 生成 Decoration.inline。
    • apply：block decoration 每次 docChanged 按块重建（读 attr）；text decoration 走 map 增量。
  3. 钩子：
    • setClass：普通节点 → 记录「节点→class 串」（写 data-dm-class / 供 inline 生成），不写真实 DOM；<html> 节点 → 由调用方决定是否加 HTML_CLASS（DM 总开关）。
    • setStyle：no-op；setAttr / getAttr：不传（用默认 property）。
  4. DM 开关：用算法暴露的 HTML_CLASS，在需要时给 <html> 加/删。
  5. 复制粘贴：内部→内部 / 内部→外部 走 doc(LM)，天然是 LM，无需特殊处理；外部→内部 在 transformPasted 调 run(片段节点, opt, container)（container = 插入点父容器）跑算法并写入 data-dm-class，继承由算法 rebuildAncestorExpando(container) 从祖先链重建。
  6. 保存：doc 恒 LM，序列化过滤 data-dm-class，直接存、无需还原。
  7. 非颜色样式编辑（font-size / margin 等）：LM === DM，正常走 mark / node attr，不进 DM 逻辑。
职责边界：算法 负责颜色转换 + 产出 <style> + 把 class 经钩子交出（含 <html> 开关 class）；调用方 负责把 class 转成 Decoration（block 经 data-dm-class、text 经 inline）、维护增量、控制 <html> 开关、保存时过滤 attr。doc 恒 LM。

十、落地待办与风险

算法侧改动清单

  • darkmode.ts：<html> 的 classList.add/remove(HTML_CLASS)（L260 / L348）改为走 setClass 钩子可接管的路径。
  • 对外导出 HTML_CLASS 常量。
  • run 增加第三个可选参数 container: HTMLElement；新增 rebuildAncestorExpando(container)（方案 A：向上遍历到根逐级 mix，继承 expando 写到片段顶层节点），调用时机在 domUtils.set 之后、switchToDarkmode 之前。
  • 确认 mode:'dark' + setClass 全链路下不再有任何「绕过钩子直接写真实 DOM class/style」的残留。

调用方改动清单

  • schema 加 data-dm-class attr（toDOM 不渲染）。
  • DM 插件：setClass 钩子落地 + DecorationSet（block 重建 / text map）+ <html> 开关控制。
  • transformPasted 调 run(片段, opt, container) 转换粘贴片段。
  • 保存链路过滤 data-dm-class。

仍需注意 / 后续验证

  • <style> 累积（已知待优化，不阻塞主流程）：每次 run（含每次粘贴）末尾 writeStyle 都 insertAdjacentHTML 注入一个新 <style>，规则只增不减——长时间编辑 + 频繁粘贴会累积上千条规则，导致内存单调增长 + 样式重算(recalc)变慢（单 class 选择器匹配本身不慢，问题在规则总量）。几百个无感，上千/上万需处理。倾向解法（后续主流程完成再做）：复用现有 reset()（本就会 removeChild 所有 js_darkmode_style__ 标签）在标签数超阈值 / 失焦 / 空闲时「合并重建」——reset + 对全文重跑一次全量 run，把规则压回 1–2 张。
  • 背景图补色是「追加一层 background」，确认算法跑视图 DOM 时读得到完整 background-image 并产出正确多层规则（背景图在 inline style 上，可读）。
  • 真实业务文档规模下的 decoration 密度与 nodeView 开销，用真实内容再量一次性能。
  • 粘贴片段经 rebuildAncestorExpando(container) 的继承结果，确认与首次全量一致（尤其嵌套在带背景祖先里粘贴的场景）。
