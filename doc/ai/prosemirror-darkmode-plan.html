ProseMirror × mp-darkmode 适配方案（定稿）

用 mp-darkmode 算法为 ProseMirror 架构编辑器做 Dark Mode 适配。本文档为多轮讨论 + 真实环境 PoC 实测后的收敛定稿，作为算法侧改造与编辑器接入的实现总纲。

背景与目标

现状算法通过「加 className + 注入 <style> + @media 媒体查询」给页面上 Dark Mode 样式（见 算法架构文档）。这在只读文章里没问题，但在编辑器里会出问题：

根因：ProseMirror 的样式必须活在它的数据/视图模型里（node attrs / marks / decorations），而「className + <style> + @media」是一条游离在 PM 模型之外的旁路 CSS——PM 的 parseDOM / toDOM / clipboard 序列化根本不认这些动态类名和外部规则。任何 split / 粘贴 / 重渲染都会让这套样式与文档模型错位（例如换行时新段落把 computed 的 DM 样式固化进 inline、丢失 LM）。

目标：让 DM 样式回到 PM 可管理的范畴，且不污染文档（doc 恒存 Light Mode）。

一、术语

名称含义适用
全包现状方案。算法包办 className + <style> + @media 全链路，样式自动生效只读文章
半包新增方案。算法只吐 per-node DM diff（DmChange[]），落地（decoration / 继承 / 粘贴）由调用方负责编辑器

二、总体架构（B(b) 纯视图方案）

  • 编辑器用半包。
  • DM 用 ProseMirror Decoration（加 class + 注入一份视图级 <style>，规则带 !important） 表达；DM 开关由 JS 控制（DM 态才生成 decoration），不用 @media。
  • doc 恒存 LM，DM 永不进文档模型 —— 这是整套方案能大幅简化的根基。
  • 对编辑器视图 DOM 跑算法（有真实布局，背景图位置判断与 posAtDOM 均可用），靠全钩子接管避免写真实 DOM，从而不触发 PM 的 DOMObserver。
为什么纯视图能绕开根因：decoration 是 PM 视图层每次渲染重新应用的、绝不进 doc。于是 split/粘贴/重渲染都不会把 DM 固化；复制粘贴走 doc 序列化天然得到 LM；保存直接存 doc（LM）无需还原。「className 由 decoration 动态挂、DM 由 JS 开关控制」替代了「className 直接写 DOM + @media」，原痛点全部消失。

三、模式切换约定

  • 以「有无传 setDmStyle 钩子」区分全包 / 半包，不新增 mode 字段。
  • setDmStyle 存在 ⇒ 自动隐含全套半包行为：不 addClass、不 genCss 选择器、不注入 <style>（隐含 noEmit），产出改为逐属性收集 DmChange 并通过 setDmStyle(el, changes) 吐出。调用方只需传这一个钩子即进入半包，不用再记得配 noEmit。
  • 对内实现仍以 config.setDmStyle !== null 作为半包判断，在 convert 产出段、diff 收集、writeStyle 注入几处切换；全包行为零变化。

四、DmChange 数据结构（定稿）

type DmChange = { prop: string; dm: string; lm?: string };
type SetDmStyle = (node: HTMLElement, changes: DmChange[]) => void;
  • prop：CSS 属性；
  • dm：该属性最终的 Dark Mode 值（必填，调用方落地 decoration 用它）——同时覆盖「替换已有属性」和「新增原本没有的属性」两种情况，统一成「最终就该是这个值」；
  • lm?：原 Light Mode 值，可选、仅调试/校验——B(b) 下 doc 恒 LM、不需要还原。

早期曾设计 replace / set / appendBg 三类 op，已收敛为单一结构：因背景图写在 inline、算法跑视图 DOM 能读到完整 background-image，可直接给整条多层值，无需 appendBg。背景图多层拆成多条 {prop, dm} 表达：

// 一个背景图节点的 changes：
[
  { prop:'background-image',    dm:'url(a.png), linear-gradient(#fff,#fff)' },
  { prop:'background-position', dm:'top left, top left' },
  { prop:'background-size',     dm:'cover, 100%' },
]

五、关键业务前提（约束了复杂度）

  • 禁色板：用户不能选中已有文本改 color / bgColor → 日常输入 / split 不产生新颜色、无继承级联重算。
  • 但粘贴外部片段会带入自定义颜色（如红字片段粘进空编辑器），且会出现渐变背景 / 背景图 / 文字描边等复杂内容 → 必须用完整算法（半包 run / convertFragment），不能只靠 getDmBgColor / getDmFontColor 纯函数（它们只处理纯色 color/bg）。

六、运行时数据流（三条路径）

① 首次全量
   对编辑器视图 DOM 跑 run()（半包）
     → 每节点产出 DmChange[]（经 setDmStyle）
     → 用 view.posAtDOM 映射到 doc position
     → 生成 decoration（加入 DecorationSet）
   expando 走默认 property 写视图 DOM（DOMObserver 监听不到，rerender 丢失无妨）

② 日常输入 / split  —— 不跑算法
   decoration 靠 DecorationSet.map(tr.mapping) 增量延展继承
   （禁色板下无新颜色、无级联重算）

③ 粘贴外部复杂片段
   transformPasted → 对片段跑 convertFragment(nodes, container)（半包增量入口）
     继承：算法从 container 沿 parentNode 向上重建祖先 expando（O(depth)），调用方不参与
     → DmChange[] → decoration

图：三条路径。只有 ① 和 ③ 跑算法，② 靠 decoration 增量跟随。

七、算法侧要做什么

  1. 新增 setDmStyle 钩子：darkmode.d.ts 加 SetDmStyle 类型 + ConfigOption.setDmStyle；config.ts 默认 null（即全包）。
  2. sdk.ts convert 加半包分支（config.setDmStyle !== null）：逐属性收集 {prop, dm, lm?}、跳过 addClass / genCss、改调 setDmStyle(el, changes)；setDmStyle 存在隐含 noEmit（darkmode.ts 不走 writeStyle 注入）。
  3. 新增 per-fragment 入口 convertFragment(nodes: HTMLElement[], container: HTMLElement)：run 的干净子集——复用已 init 的 config / 阈值，只对片段直出，不碰首屏 / 整篇注入。nodes 为要转换的片段节点，container 为其父容器（插入点父节点）。算法内部从 container 沿 parentNode 向上收集祖先链、自顶向下读各祖先 LM 内联色并逐级 mix，重建出 container 处的继承 expando（即 rebuildAncestorExpando(container)），再对 nodes 半包 convert——继承计算全在算法内部，调用方不传继承起点。祖先无背景色时 fallback 到 config.defaultLightBgColor；若祖先带背景则精确继承。
  4. 背景图 bgStack 产出路径改造（半包最需小心的点）：
    • 背景图节点的多层 background 通过 setDmStyle 发给该节点（替代原 genCss(bgStackClassName, …)）；
    • bgStack.contains 矩形相交保留（视图 DOM 有真实布局），但命中后的产出改走 setDmStyle 而非 genCss。
    普通 color / border / shadow 的替换反而简单，背景图 / 文字底图这条延迟产出链才是重点。
  5. 半包下不触碰真实 DOM 的 attribute / style（否则触发 DOMObserver）：
    • 清 !important 的 setStyle（sdk.ts 调用点不改）→ 由调用方传 no-op 兜底（半包不需清，decoration 内层 !important 自然覆盖）；
    • addClass / setClass：半包分支本就不调用；
    • setAttr / getAttr / removeAttr：默认 expando property，MutationObserver 监听不到。
  6. 编辑器场景配置：needJudgeFirstPage:false、delayBgJudge:false。
  7. 全包行为零变化（以 setDmStyle 有无隔离，保护只读文章存量）。

八、调用方（编辑器）要做什么

  1. DM 插件（核心）：维护 DecorationSet
    • init：首次对视图 DOM 跑 run()（半包）→ 在 setDmStyle 回调里收集每节点 DmChange[] → view.posAtDOM 映射到 doc position → 生成 decoration 加入 DecorationSet；
    • apply：切 DM 开关 → 全量重算 buildDecos；文档变化 → DecorationSet.map(tr.mapping, tr.doc) 增量延展（日常输入 / split 走这条，不跑算法）；
    • 注入一份视图级 <style>（DM class 规则 + !important），由 JS 开关控制是否生成 decoration（不用 @media）。
  2. decoration 生成规则：text 的 color / 描边（-webkit-text-stroke 等）→ Decoration.inline（加 class+!important，class 在内层盖住 mark inline color）；block 的背景 / 渐变 / 背景图多层 → Decoration.node。
  3. 钩子：实现 setDmStyle（diff→decoration）；传 setStyle / setClass 为 no-op；setAttr / getAttr 不传（用默认 property）。
  4. 继承（调用方无需处理）：继承全由算法 expando 机制承担。粘贴时调用方只需把片段节点 nodes 和插入点父容器 container 传给 convertFragment，算法自己从 container 向上重建继承。（早期「轻量路线」里由调用方维护的「继承 dmBg 栈」仅适用于只用 getDm* 纯函数的场景，本重路线方案不需要。）
  5. 位置映射：用 PM 原生 view.posAtDOM / domAtPos 把算法按 DOM 产出的 diff 映射到 doc position。
  6. 复制粘贴：内部→内部 / 内部→外部 走 doc(LM)，天然是 LM，无需特殊处理；外部→内部 在 transformPasted（或 handlePaste）对片段跑 convertFragment(nodes, container)（container = 插入点父容器），继承由算法从 container 向上重建、调用方不参与。
  7. 保存：doc 恒 LM，直接存，无需任何还原 / 合并。
  8. 非颜色样式编辑（font-size / margin 等）：LM === DM，正常走 mark / node attr，不进 DM 逻辑、不进 decoration，保存无需处理。
  9. 配置：调 run / init 时传 needJudgeFirstPage:false、delayBgJudge:false 及上述钩子。

两侧职责边界（一句话）

算法：吃 DOM（首次=视图 DOM；增量=片段 nodes + container）→ 产出 per-node DmChange[]（经 setDmStyle），继承 / 渐变 / 背景图补色 / 描边全包内；不碰真实 DOM attribute/style。
调用方：把 DmChange[] + 节点 → 映射成 ProseMirror decoration 并维护增量；doc 恒 LM，保存 / 复制 / 非颜色编辑一概按常规走。

九、相比最初方案的简化（务必对齐）

最初设想B(b) 下结论
DM 写 inline、LM 存 data-lm-style attr取消 —— doc 恒 LM，无需存 LM 副本
保存时 data-lm-style 还原回 inline、清 DM取消 —— doc 本就是 LM，直接存
复制粘贴特殊保留 / 还原 LM大幅简化 —— 走 doc(LM) 天然正确，只剩「外部→内部」要跑算法
dmExpando attr 持久化 + 序列化取消 —— expando 退化为「一次转换内写视图 DOM property 的临时态」，用完即弃
非颜色样式 (font-size/margin) 保存时合并取消 —— LM===DM，正常走 mark / node，不进 DM 逻辑
关于 expando 与 WeakMap<PMNode>：PMNode 不可变，编辑后旧 node 被新 node 替换，WeakMap<PMNode> 会失效，不能做跨编辑的持久缓存。B(b) 下根本不需要持久化 expando：它只是「一次转换遍历内、写在（视图/临时）DOM property 上的临时态」，转换完提取出 DmChange 即弃；跨编辑的继承由 ① decoration 区间延展 ② 粘贴时 convertFragment(nodes, container) 从 container 向上重建祖先 expando 两者承担。

十一、落地待办与风险

算法侧实现清单

  • darkmode.d.ts：SetDmStyle / DmChange 类型 + ConfigOption.setDmStyle
  • config.ts：setDmStyle 默认 null
  • sdk.ts convert：半包分支（收集 diff / 跳过 addClass+genCss / 调 setDmStyle）
  • darkmode.ts：半包隐含 noEmit、不走 writeStyle；新增 convertFragment 入口
  • bgStack 产出路径：多层 background 与 contains 命中产出改走 setDmStyle

仍需注意 / 后续验证

  • 背景图 bgStack 延迟产出链在半包下的改造是最易出错处，建议优先写单测 / PoC 覆盖。
  • 真实业务文档规模下的 decoration 密度与 nodeView 开销，用真实内容再量一次性能。
  • convertFragment(nodes, container) 内 rebuildAncestorExpando(container)（从 container 向上重建继承）的边界场景：祖先无色 fallback、带背景祖先的精确继承、遍历终点（根容器 / body）。
